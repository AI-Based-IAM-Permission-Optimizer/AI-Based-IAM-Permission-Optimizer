# AI-Based IAM Permission Optimizer — ML Model & Output Documentation

**Project:** AI-Based IAM Permission Optimizer  
**ML component:** IAM Permission Risk Scoring Model  
**Current model version:** `iam-risk-v2`  
**Primary implementation:** Python, pandas, NumPy, scikit-learn, optional XGBoost  
**Execution environment:** Jupyter Notebook for development; packaged model for backend/Lambda inference

---

# 1. ML Model Purpose

The ML component analyzes IAM permission/activity data and estimates whether an IAM permission is likely to be excessive.

The model is intended to support least-privilege IAM analysis.

The ML stage produces:

```text
IAM permission/activity data
        ↓
Feature engineering
        ↓
ML model
        ↓
Calibrated risk score
        ↓
Prediction
        ↓
Recommendation
        ↓
Backend / Admin Dashboard
```

The model does not directly modify IAM permissions.

The final recommendation can be reviewed and approved by an administrator before any policy change is made.

# 3. Target Variable

The binary ML target is:

```text
INTENDED   → 0
EXCESSIVE  → 1
```

Target creation:

```python
target = (permission_status == "EXCESSIVE").astype(int)
```

The model therefore estimates:

```text
P(EXCESSIVE | IAM permission and activity features)
```

---

# 4. Important Separation: ML Score vs IAM Risk Weight

These two values must not be confused.

## risk_score

Generated by the ML model.

```text
Range: 0.0 to 1.0
```

Meaning:

```text
Estimated calibrated probability that the permission is EXCESSIVE
```

Examples:

```text
0.10 → approximately 10% estimated probability
0.50 → approximately 50%
0.90 → approximately 90%
```

These examples do not define a universal prediction threshold.

## risk_weight

Provided by the IAM security/risk catalogue.

Example concept:

```text
1  → low catalogue risk
8  → high catalogue risk
10 → very high catalogue risk
```

`risk_weight` is security metadata, not the ML probability.

# 5. Model V2 Feature Design

The improved model uses features intended to generalize better to unseen users/actions.

## 5.1 Behavioral Features

```text
usage_count
log_usage_count
unique_days_used
log_unique_days_used
days_since_last_use
active_days
usage_frequency
success_rate
smoothed_failure_rate
```

### Why log features are used

Usage counts can have a large range.

The model therefore uses:

```python
np.log1p(usage_count)
```

to reduce the dominance of very large counts.

# 7. Security-Sensitive Features

Derived flags can include:

```text
is_delete
is_permission_change
is_security_sensitive
```

These help the model distinguish privilege-sensitive operations.

For example:

```text
s3:DeleteObject
iam:AttachRolePolicy
iam:DeleteUser
```

can carry different security implications from read-only actions.

The values ultimately come from the risk/operation metadata supplied by the security pipeline.

---

# 8. Resource Scope Features

When resource information is available, the model can derive:

```text
is_wildcard_resource
scope_breadth
```

Example:

```text
resource = "*"
```

can indicate broad scope.

Raw ARNs and raw resource identifiers should not be used directly as high-cardinality model features.

---

# 9. Features Intentionally Avoided

The improved model should avoid using the following as direct predictive features:

```text
user_id
```

Reason:

```text
The model may memorize a specific user's behavior
instead of learning general permission patterns.
```

Also avoid using:

```text
raw resource ARN
```

because ARNs are generally high-cardinality identifiers.

`role_id` and exact `action` should be treated cautiously because they can also encourage memorization when synthetic datasets contain deterministic role/action labels.

Context such as position/department/team can be introduced when reliable independent data is available.

# 11. Risk Catalogue Integration

The usage dataset is joined with the IAM risk catalogue using:

```text

```

The merge should be:

```python
validate="many_to_one"
```

This ensures a permission action maps to a single catalogue record.

The pipeline checks that catalogue values are consistent for:

```text

```

# 12. Synthetic Data / Label Leakage Risk

The original dataset contains an important issue that must be monitored.

In the existing synthetic data, `usage_count` is strongly associated with the target. In particular, the observed data showed patterns where some usage-count ranges were almost deterministically associated with `INTENDED` or `EXCESSIVE`.

This creates the risk that the ML model simply learns:

```text
usage_count
      ↓
permission_status
```

instead of learning realistic IAM permission behavior.

A simple model using only `usage_count` should therefore be treated as a label-leakage audit.

If a usage-count-only model achieves unusually high performance, the synthetic data should be regenerated.

---

# 13. Recommended Synthetic Data Generation

For a realistic training dataset, the generation process should be:

```text
Role / Position
      ↓
Required permissions
      +
Intentionally excessive permissions
      ↓
Ground-truth permission status
      ↓
Simulated AWS activity
      ↓
Activity aggregation
      ↓
ML features
      ↓
Training dataset
```

The label should be established independently from the activity features.

This prevents the model from learning an artificial rule such as:

```text
usage_count < 5 → EXCESSIVE
```

---

# 14. Train / Validation / Test Strategy

The improved pipeline uses group-aware splitting.

Primary grouping field:

```text
user_id
```

The purpose is to avoid having the same user's records in both training and evaluation data.

Conceptually:

```text
Training users
       ↓
Validation users
       ↓
Holdout test users
```

User overlap between independent evaluation groups should be:

```text
set()
```

when the split is successfully isolated.

# 16. Model Selection

The primary comparison metric for an imbalanced IAM problem is:

```text
PR-AUC
```

Additional metrics:

```text
Precision
Recall
F1 score
ROC-AUC
Accuracy
Balanced Accuracy
MCC
Brier Score
Log Loss
```

For the `EXCESSIVE` class, precision, recall and F1 are especially important.

---

# 17. Precision, Recall and F1

## Precision

Among permissions predicted as `EXCESSIVE`, precision measures how many are actually excessive.

```text
Precision = TP / (TP + FP)
```

High precision reduces unnecessary reviews/removals.

---

## Recall

Among all truly `EXCESSIVE` permissions, recall measures how many the model identifies.

```text
Recall = TP / (TP + FN)
```

High recall reduces missed excessive permissions.

---

## F1 Score

F1 balances precision and recall.

```text
F1 = 2 × Precision × Recall / (Precision + Recall)
```

---

# 18. Why Accuracy Is Not Enough

The `EXCESSIVE` class is smaller than the `INTENDED` class in the current dataset.

A model can obtain high accuracy while still missing excessive permissions.

Therefore, the project should not use accuracy as the only success criterion.

The evaluation should include:

```text
PR-AUC
EXCESSIVE precision
EXCESSIVE recall
EXCESSIVE F1
confusion matrix
```

---

# 19. Probability Calibration

The model's raw `predict_proba()` output should not automatically be treated as a trustworthy probability.

Model V2 therefore includes a calibration step.

Conceptually:

```text
Raw model score
       ↓
Calibration model
       ↓
Calibrated risk_score
```

The final `risk_score` is intended to be:

```text
0.0–1.0 calibrated excessive probability
```

Calibration quality can be checked using:

```text
Brier score
Log loss
Calibration curve
```

---

# 20. Prediction Threshold

The model should not permanently use:

```text
threshold = 0.50
```

Instead, the operating threshold is selected using validation data.

Example policy requirement:

```text
minimum acceptable EXCESSIVE recall
```

Then among thresholds satisfying that requirement, choose a suitable operating point based on validation metrics.

The threshold is part of the production model configuration.

---

# 21. Threshold vs Recommendation

These are separate concepts.

### ML layer

```text
risk_score
     ↓
prediction
```

### Policy layer

```text
risk_score
+
risk_weight
+
resource scope
+
security guardrails
     ↓
KEEP / REVIEW / REMOVE
```

Therefore a high `risk_score` does not automatically mean an IAM permission is deleted.

---

# 22. Recommendation Logic

Possible values:

```text
KEEP
REVIEW
REMOVE
```

## KEEP

The permission can remain without an immediate reduction recommendation.

## REVIEW

An administrator should review the permission before making a change.

## REMOVE

The permission is recommended for removal, but administrator approval is still required.

---

# 26. Example Interpretation

For:

```json
"risk_score": 0.9142
```

the intended interpretation is:

```text
The calibrated model estimates approximately a 91.42%
probability that this permission is EXCESSIVE.
```

For:

```json
"prediction": "EXCESSIVE"
```

the calibrated score crossed the configured operating threshold.

For:

```json
"recommendation": "REVIEW"
```

the system is asking an administrator to review the permission.

It does not mean the IAM permission has been changed.

---

# 27. Why a High-Risk Permission Can Still Be REVIEW

Example:

```json
{
  "risk_score": 0.9142,
  "risk_weight": 8,
  "prediction": "EXCESSIVE",
  "recommendation": "REVIEW"
}
```

This is valid.

The ML prediction and security recommendation have different responsibilities:

```text
ML:
"How likely is the permission excessive?"

Policy layer:
"What should the system recommend?"

Administrator:
"What should actually happen?"
```

# 29. Overfitting Detection

The pipeline compares training and validation performance.

A large train-validation gap can indicate overfitting.

Example:

```text
Train PR-AUC = 0.99
Validation PR-AUC = 0.70
```

would require investigation.

Potential responses include:

```text
reduce model complexity
increase regularization
reduce high-cardinality features
improve synthetic data
remove leakage
increase data diversity
```

---

# 30. Underfitting Detection

Underfitting can appear when both training and validation performance are low.

Potential responses include:

```text
improve feature engineering
increase model capacity carefully
add missing contextual features
improve data quality
increase training diversity
```

The solution should not simply be "use a bigger model."

---

# 31. Feature Importance

The evaluation stage should include permutation importance on held-out validation data.

The goal is to determine which features actually contribute to validation performance.

Features that dominate the model unexpectedly should be investigated for:

```text
leakage
synthetic generation artifacts
data quality issues
memorization
```

---

# 32. Robustness Tests

The production model should be tested with:

```text
missing numeric values
missing categorical values
unseen categorical values

boundary risk scores
empty or malformed input
```

The pipeline should produce either:

```text
valid prediction
```

# 40. Important Limitations

The model is a decision-support component.

Performance obtained on synthetic data does not automatically establish real-world IAM generalization.

The synthetic data should contain:

```text
legitimate rare-use permissions
frequently used excessive permissions
high-risk permissions that are genuinely necessary
low-risk permissions that can still be excessive
different roles
different users
different services
different resource scopes
```

This diversity helps prevent the model from learning simplistic rules.

---

# 41. Recommended Production Principles

```text
1. Never use accuracy alone.
2. Keep user identity out of predictive features.
3. Avoid raw high-cardinality identifiers.
4. Check synthetic-label leakage.
5. Use group-aware validation.
6. Tune hyperparameters using validation/CV only.
7. Tune the classification threshold separately.
8. Calibrate risk probabilities.
9. Inspect false negatives.
10. Test missing and unseen values.
11. Store model version with every recommendation.
12. Keep ML prediction separate from security policy logic.
13. Never let ML directly delete IAM permissions.
14. Keep administrator approval in the final workflow.
```
